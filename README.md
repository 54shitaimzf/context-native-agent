# Agent 重架构：迈向上下文原生智能（Context-Native Agent）

一篇约 2.4 万字的中文长文（序言 + 正文 + 三个附录），讲的是一件很具体的事：**AI 干活时"摆在眼前"的那些内容，该怎么管。**

## 这篇在说什么

AI 干活，靠的是每一轮喂给它的那段内容（行话叫"上下文"）：装什么、装多少，直接决定它干得好不好、以及花多少钱。

行业里的通行做法是把内容一段一段往里加，加不下了就让 AI 自己写一份摘要、把原文删掉。麻烦在于：**删掉的东西如果后面又要用，就只能重新想一遍——而"想"是所有动作里最贵的。**

这篇文章的主张只有一句：**把"上下文"从框架里拆出来，让它成为一等公民。** 拆开之后，问题本身换了一个：

- 旧写法里，上下文是一段**必须被管理的缓冲区**。要它变小，唯一的手段是压缩，而压缩是**删除、不可逆**——于是所有解法都被挤到同一条路上：在信息量与长度之间做取舍。做取舍就必然丢东西，就必然要赌。
- 新写法里，上下文是一份**可以从环境重新装出来的投影**。不装，只是此刻不需要；**不装不等于删掉**。原文一直在文件里，要用的时候读一次就行。

**所以被换掉的不是某个机制，而是问题的解空间。** 文章用一棵 Git 树给出了一种具体做法——主 Agent 拆活、多个子 Agent 并行干、合并之后重写需要更新的那一段、每一轮从环境重新装一次上下文——但那只是这个新空间里的**一个点**：粗糙、可以替换，甚至可能是错的。要立住的是那个空间。

## 它到底省不省

用一次 2,068 步的真实任务算：

| 怎么用 | 账单 |
| --- | --- |
| 现行做法，人在实测的停手位置压缩 | ¥7.02 |
| 现行做法，完全不管控 | ¥16.97 |
| 这套做法 | **¥5.70** |

这笔账是**压着自己算**的：对自己不利的量一律往大取，对自己有利的量一律不计（模型能力上的好处、少走的弯路、延迟与吞吐，全部按 0 算）。只有**四条例外**，一条条列在附录2 的 A2.7 里，各自交代把结论推到哪一步。

要让这笔账成立，设计上得守住三件事：每轮常驻的上下文压得住，每轮真正写出去的量足够小，内容没变的那部分能一直复用。附录2 给了这三个量的算法。

而"水位为什么能压低"这一条，是这套做法里最该记住的：**先全量理解，再拆分。** 理解被编译进那段稳定的前缀，具体干活的时候只装自己那一片，缺什么按需读一次——**低水位不是设计出来的，是拆分出来的**。现状做不到，是因为它只有一层上下文，理解与干活挤在一起；串行又不拆分，它就不可能不带着足量的信息工作。

还有一处要说清：**这笔账量的是文中那处具体实现（Git 树）**。换一处实现、换一组参数，数字会变，而账的算法与这三件事的形状不变。
